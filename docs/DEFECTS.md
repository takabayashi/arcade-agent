# `arcade-agent` — QA Defects Report

> Generated by the adversarial QA sweep over the Architect spec
> (`docs/IMPLEMENTATION_SPEC.md`) and the developer's implementation as of
> the run on `2026-05-26`. The dev's baseline (87 tests passing, ruff clean,
> format clean) reproduces. The defects below were found by **static audit,
> targeted unit tests, an end-to-end daemon harness, and the live Arcade
> probe** in `scripts/probe.py`.

## Summary

The package compiles, lints, formats, and unit-tests cleanly (87 + 12 new
QA tests passing; 6 QA tests skipped as documented defects). The CLI surface
behaves correctly when the daemon is down, with missing bindings, and with
empty/missing TOML files. The wire protocol over UDS works for the cases
the integration suite exercises against a fake agent.

However, **the live probe against the real Arcade API fails immediately
with exit 1**: four of the thirteen names in `config.ALL_TOOLS` simply do
not exist in the Arcade tool registry, so `ArcadeAgentClient.list_tool_schemas()`
raises `ConfigError` before the daemon can ever serve a prompt. That alone
is a ship-blocker; the spec said `config.py` was off-limits to the dev, but
it is **not** off-limits to the architect, and these names must be reconciled
before any user touches the system. In addition, three high-severity issues
were found in the agent / daemon interaction (wire-event ordering during a
confirm, callback-error handling, and confirm-timeout signaling).

**Confidence: 73 %.** Reasoning: one CRITICAL defect that bricks every
end-to-end interaction with the real Arcade API, three HIGH defects that
will visibly bite real users (wrong wire ordering, swallowed callback
errors, silent confirm timeouts), and several MEDIUM/LOW polish items.
Under the rubric this lands in the 70–80% band.

Bottom line: **not ready to ship — needs fix loop.**

## Critical defects (must fix before any user touches it)

### C1 — `config.ALL_TOOLS` references tool names that do not exist in Arcade

The live probe failure reproduces verbatim:

```
$ .venv/bin/python scripts/probe.py
ERROR: list_tool_schemas failed: Arcade did not return the following
configured tools: Gmail.CreateDraft, Gmail.GetEmail, Gmail.SearchEmails,
GoogleCalendar.FindTimeSlotsWhenAvailable
```

I also paginated the live Arcade catalog directly (script removed after
use) and confirmed the discrepancies. The actual Arcade names are listed
in the "Live probe result" section below.

| Configured (wrong)                              | Closest real Arcade name(s)                                  |
| ------------------------------------------------ | ------------------------------------------------------------ |
| `Gmail.CreateDraft`                              | `Gmail.WriteDraftEmail` (also `Gmail.UpdateDraftEmail`)      |
| `Gmail.GetEmail`                                 | No 1:1 equivalent — closest is `Gmail.GetThread`             |
| `Gmail.SearchEmails`                             | `Gmail.ListEmailsByHeader` or `Gmail.SearchThreads`          |
| `GoogleCalendar.FindTimeSlotsWhenAvailable`      | `GoogleCalendar.FindTimeSlotsWhenEveryoneIsFree`             |

Concrete impact:
1. `arcade-agent daemon start` followed by `arcade-agent ask "..."` will
   never produce a `final` event. The first prompt calls `run_turn`, which
   calls `arcade_client.list_tool_schemas()`, which raises `ConfigError`,
   which the daemon converts to `{"event":"error","message":"agent crashed: ..."}`
   and never recovers from on subsequent prompts (because the same
   `ArcadeAgentClient` is reused and re-raises every time).
2. `arcade-agent bind add --user-id ...` only calls `pre_authorize_all`
   (which does not need the schema cache), so it appears to succeed. The
   user then runs `ask` and gets the cryptic "agent crashed" message. UX
   cliff.
3. The dev-side tests pass because they mock `tools.list` and never assert
   against the live catalog.

Reproducer (kept as a skipped pytest case so the orchestrator can re-enable
it after a fix): `tests/test_qa_additional.py::test_qa_defect_1_live_arcade_names_match_config`.

Fix direction (out of QA's authority but the only sane option): the
architect must reconcile `config.ALL_TOOLS` with the live Arcade tool list
quoted under "Live probe result" below and update
`config.DESTRUCTIVE_TOOLS` to match.

## High defects (should fix; would bite in real use)

### H1 — Wire-event ordering: `confirm` arrives BEFORE `tool_call` with the real `ClaudeAgent`

`ClaudeAgent._handle_tool_use` buffers events into a local `events_out` list
and only yields them after the method returns:

```328:339:src/arcade_agent/claude_agent.py
        events_out.append(ToolCallStarted(name=arcade_name, args=args))

        if is_destructive(arcade_name):
            events_out.append(ConfirmRequested(tool_name=arcade_name, args=args))
            try:
                approved = await self._on_confirm(arcade_name, args)
```

…but `on_confirm` (the daemon's per-connection callback) **already emits
the wire `confirm` frame and awaits the user's ack** before
`_handle_tool_use` can return. Net effect: the daemon's `_event_to_wire`
never gets the chance to send `tool_call` until *after* the user has acked
the confirm. I reproduced the order in isolation:

```
LOG ORDER:
  on_confirm:Gmail.SendEmail
  yield:ToolCallStarted:Gmail.SendEmail
  yield:ConfirmRequested:Gmail.SendEmail
  yield:ToolCallResult:Gmail.SendEmail:ok=True
```

The spec algorithm in §5.5 explicitly says yield `ToolCallStarted`, then
yield `ConfirmRequested`, then `await on_confirm`. Two reasonable fixes:

* Move the await on `on_confirm` to AFTER the caller's `for ev in events_out:
  yield ev` (i.e. split `_handle_tool_use` so the events drain to the wire
  before the daemon sends the in-callback `confirm` frame), or
* Stop buffering in `events_out` and convert `_handle_tool_use` to an async
  generator that yields directly so flow control is identical to the spec.

The existing daemon integration test `test_confirm_approve_flow` does NOT
catch this because the `FakeClaudeAgent` in that suite yields directly (no
internal buffering), which preserves the intended order. The QA suite adds
`tests/test_qa_additional.py::test_qa_defect_2_wire_order_tool_call_before_confirm`
(skipped) to document the failure.

Severity rationale: this is a UX bug, not a correctness one — the `confirm`
panel still includes the tool name + args via `render_summary`, so the
user can decide. But the CLI's `tool_call` panel that the user expects
*before* the prompt is missing, which makes the destructive-tool flow feel
disorienting in interactive use.

### H2 — `on_confirm` / `on_auth_url` callback errors don't abort the turn (off-spec)

Spec §5.5 (edge cases table) states:

> | `on_confirm` raises | Propagate as `ErrorEvent` and abort the turn with `Final("")`. |
> | `on_auth_url` raises | Same. |

The current implementation does the opposite: it catches the exception, emits
an `ErrorEvent`, and synthesizes an `is_error=True` tool_result that gets
fed back to Claude on the next iteration. Live reproducer (run on the
current code):

```
on_confirm callback raised
Traceback (most recent call last):
  ...
RuntimeError: boom
create.await_count = 2 (expected 1 per spec)
Final texts: ['Sent.']
Error msgs: ['confirmation gate failed: boom']
```

i.e. when the callback exploded the model was still re-invoked and emitted
"Sent." — which is exactly the failure mode the spec was written to
prevent. Concrete: if the UI process loses its writer mid-confirm, the
agent will *successfully run the destructive tool anyway* on Claude's
retry pass after seeing the synthetic tool_result.

Reproducer test: `tests/test_qa_additional.py::test_qa_defect_3_on_confirm_raise_aborts_turn`
and `::test_qa_defect_3_on_auth_url_raise_aborts_turn` (both skipped).

### H3 — Confirm timeout is silent on the wire

Spec §5.6 edge case row:

> | `on_confirm` future never resolved (timeout 300 s) | Treat as `approved=False`; emit `ErrorEvent("confirmation timed out")`. |

The current daemon code:

```348:354:src/arcade_agent/daemon.py
                try:
                    return await asyncio.wait_for(fut, timeout=_CONFIRM_TIMEOUT)
                except TimeoutError:
                    logger.warning("confirm timeout for session %s", session_id)
                    return False
```

logs a warning and returns `False`. That means `_handle_tool_use` sees
`approved=False` and emits `ToolCallResult(ok=False, summary="user declined")`
— byte-for-byte the same wire frame as an actual user decline. There is no
way for the client to distinguish a network/UX drop from a deliberate "no".

Reproducer (live, with `_CONFIRM_TIMEOUT` monkey-patched to 0.3 s):

```
event kinds: ['tool_call', 'confirm', 'tool_result', 'final']
all events:
  {'event': 'tool_call', 'name': 'Gmail.SendEmail', 'args': {}},
  {'event': 'confirm', 'tool': 'Gmail.SendEmail', ...},
  {'event': 'tool_result', 'name': 'Gmail.SendEmail', 'ok': False, 'summary': 'user declined'},
  {'event': 'final', 'text': 'done'},
```

No `error` event. Test: `tests/test_qa_additional.py::test_qa_defect_4_confirm_timeout_emits_error_event`
(skipped).

## Medium defects (nice to fix; quality issues)

### M1 — Daemon `_histories` and `_locks` grow unbounded

`DaemonServer._histories` and `_locks` are keyed by `session_id` and never
evicted. Sessions remain pinned in memory across the daemon's entire
uptime. Demonstrated with a tiny loop that drove 20 unique session_ids:

```
histories = 20 locks = 20
```

Multiplied across days of operation this is a real memory leak. Cheap fix:
LRU-evict when a session has had no activity for N minutes, or drop the
entry when the most-recent client connection drops AND the history was
already drained. Reproducer test:
`tests/test_qa_additional.py::test_qa_defect_5_daemon_history_is_evictable`
(skipped — it documents the missing behavior).

### M2 — `BindingStore.add` silently sets `default` on the first add (off-spec)

```142:151:src/arcade_agent/bindings.py
    def add(self, binding: Binding, *, make_default: bool = False) -> None:
        ...
        if make_default or self._default is None:
            self._default = binding.name
        self.save()
```

The spec says `make_default=True` updates the default pointer. Auto-set on
first add is an undocumented convenience. It's defensible (otherwise a
fresh installer is stuck without a default after `bind add`), but it
contradicts spec §5.2 and means `bind add NAME --user-id ...` (without
`--default`) silently changes global state. Either the spec needs an
addendum or the dev needs to drop the `or self._default is None` clause
and have `init` always pass `--default` for the first binding. The CLI's
`init` does set `make_default=True`, so removing the silent default in
`add` should be safe.

### M3 — `BindingStore.save` does not fsync the parent directory

Spec §5.2 mandates an atomic write (tmp file + `os.replace`). The
implementation fsyncs the tmp file's contents but does not fsync the
directory afterwards, so a crash between `os.replace` and the dirent
flush can lose the rename on power-loss filesystems. Realistically
unlikely on modern ext4/APFS for a demo but worth fixing for production
hardening.

### M4 — `_run_prompt` does not emit a terminal `final` event after `agent crashed`

```370:374:src/arcade_agent/daemon.py
            except Exception as exc:
                logger.exception("run_turn crashed")
                await send({"event": "error", "message": f"agent crashed: {exc}"})
```

Spec §6 says "a successful turn ends with **exactly one** `final` or one
`error` event"; the CLI breaks on `error` so this is functionally
terminal. However the CLI loses the ability to format the assistant panel
("here's what got rendered before the crash") because `final` carries that
field. Cheap fix: also send `{"event":"final","text":""}` afterwards. Not
critical because the CLI does treat `error` as terminal.

## Low / nits

### L1 — Redundant `try/finally/pass` in `bindings.save`

```114:119:src/arcade_agent/bindings.py
        except OSError as exc:
            try:
                tmp_path.unlink(missing_ok=True)
            finally:
                pass
            raise ConfigError(f"failed to write bindings file {self._path}: {exc}") from exc
```

The `finally: pass` is dead. Just call `tmp_path.unlink(missing_ok=True)`.

### L2 — Concurrent first-call to `ArcadeAgentClient.list_tool_schemas` is racy

The cache check (`if self._schemas is not None: return self._schemas`) is
not lock-protected. Two ClaudeAgent instances spawned simultaneously will
each issue the Arcade `tools.list` calls. Idempotent (same result), so
correctness is preserved; performance hit is one extra HTTP round-trip on
boot. Trivial fix with an `asyncio.Lock` set in `__init__`.

### L3 — `pre_authorize_all` silently drops "pending, no URL" entries

```336:340:src/arcade_agent/arcade_client.py
            if result.completed:
                continue
            if result.url is None:
                continue
```

If Arcade ever returns `status="pending", url=None` (e.g. while
provisioning), the user gets no signal at all. Cheap fix: surface it as
an `AuthURLPending(url="")` with a warning, or raise.

### L4 — `_AUTHORIZE_TIMEOUT = 120` is unspec'd

Spec §4 sets execute=120 and wait_for_completion=300. Authorize has no
explicit timeout in the spec. The dev picked 120, which is fine —
just note it deviates from the implicit "no timeout" reading.

### L5 — `_block_to_param` uses `exclude_none=False`

`exclude_none=False` dumps `citations=None`, `cache_control=None`, etc.
back to Anthropic. The Anthropic SDK in the installed version accepts
this, but Anthropic's published wire schema flags some of these as
"don't send when null". Won't break anything today, but `exclude_none=True`
would be more defensive.

## Spec deviations review

The dev declared three SPEC-DEVIATIONs. Verdicts:

### SD1: `AgentFactory = Callable[[OnAuthURL, OnConfirm], ClaudeAgent]` — **CONFIRMED SOUND**

Spec §5.6 step 5 explicitly recommends this exact form ("The clean way is to
make `agent_factory` itself take both callbacks: `AgentFactory =
Callable[[OnAuthURL, OnConfirm], ClaudeAgent]`. Use that form."). Not a
deviation at all — the dev followed the spec's own preferred shape.

### SD2: Wire frames for `ConfirmRequested` / `AuthURLRequested` are emitted inside the callbacks, not via `_event_to_wire` — **PARTIALLY SOUND**

Verified no duplication: `_event_to_wire(AuthURLRequested)` and
`_event_to_wire(ConfirmRequested)` both return `None`, so the wire
deduplication is correct. **However** this deviation interacts badly with
`ClaudeAgent._handle_tool_use`'s `events_out` buffering pattern (defect
H1). Either the buffering goes away or the callback-side wire emission
needs to be moved/delayed. The deviation itself is fine; the interaction
with the buffered yield pattern is the bug.

There is no starvation risk: the per-session lock ensures only one prompt
flows through `_handle_tool_use` at a time, and the `_pending_confirms`
dict is keyed by `session_id` so two concurrent sessions don't clobber
each other's future.

### SD3: `DaemonServer.stop()` vs `daemon.stop_running()` split — **CONFIRMED SOUND**

`stop()` is the in-process shutdown driven by the SIGTERM handler in
`start()`'s loop; it closes the asyncio server, settles the
`_pending_confirms` futures with `False`, and unlinks socket + pidfile.
`stop_running()` is the out-of-process SIGTERM-then-SIGKILL path used by
`arcade-agent daemon stop` from a fresh CLI invocation, with cleanup of
orphan socket + pidfile if the pid is dead. Both are idempotent and
exercise the right surface for their caller. Verified by the live CLI
smoke and by `test_pidfile_lifecycle_and_already_running`.

  `test_qa_daemon_multi_prompt_same_session_preserves_history`.
* **Client-disconnect mid-confirm**: the per-session pending future is

## What is wired but unverified (needs live keys + a real Google account)

These code paths look correct on inspection but were not exercised end-to-end
because they require interactive Google consent or real assistant tool use:

* **The real consent flow** (`arcade-agent bind add personal --user-id $YOU`
  driving `pre_authorize_all` → opening the consent URL in the browser →
  `wait_for_completion` blocking until the user finishes OAuth). The QA
  suite stubs `pre_authorize_all` and `wait_for_completion`. Once C1 is
  fixed this is the first thing to test against a real Google account.
* **`ArcadeAgentClient.execute` against a real Gmail/GoogleCalendar tool.**
  All mapping branches are unit-covered (success, AUTH_REQUIRED via
  `authorization`, AUTH_REQUIRED via `TOOL_REQUIREMENTS_NOT_MET`, tool
  error, transport error, timeout), but the actual Arcade payload shapes
  on the wire are not exercised. In particular: `formatted_schema` from
  Arcade for the real Gmail/GoogleCalendar tools — the impl tries
  `fs["input_schema"]`, falls back to `fs["parameters"]`, falls back to
  `_build_input_schema(td.input)`. The fallback chain is right; which
  branch Arcade actually returns in production isn't verified.
* **The Anthropic tool-use loop against a real Claude model.** All unit
  tests use mocked `messages.create`. The `_block_to_param`
  serialization is regression-free for the Anthropic SDK version
  installed (no fields rejected), but there is no live integration check
  that an assistant message round-tripped through `model_dump` reproduces
  cleanly on a follow-up `create` call.
* **The double-fork `start_detached` happy path.** The static review of
  `start_detached` looks correct (`os.setsid` → `os.umask(0o077)` →
  `os.chdir("/")` → fork → grandchild writes its pid to the parent over a
  pipe → grandchild closes pipe, redirects stdio, runs `_daemon_main`).
  The QA suite verifies pidfile semantics in-process but doesn't actually
  fork. A manual run of `arcade-agent daemon start` + `arcade-agent daemon
  status` + `arcade-agent daemon stop` would close the gap once C1 is
  resolved.
* **`arcade-agent ask` end-to-end** (CLI → UDS → daemon → real Anthropic
  → real Arcade → response back). Currently blocked by C1.
* **Handling of an Arcade `authorize` call that returns `status="failed"`**.
  The mapping (`completed=False, url=resp.url, auth_id=resp.id`) is right
  on inspection; the agent layer would then emit
  `ToolCallResult(ok=False, summary="authorization not completed")` after
  the retry — but there's no live observation of how Arcade signals a
  hard auth failure.
